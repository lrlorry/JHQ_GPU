## 一、结论

| 变体 | 判定 | 依据 |
|---|---|---|
| **V1 E8-JHQ** | **CONDITIONAL GO（弱）** | 量化质量明显改善：primary MSE −15–21%，最终重建 MSE −34–45%，recall 平台小幅提高。但近邻排序几乎没变，固定 T 的 recall 只在小预算处显著提高（测试集 vogue T=80 时 +1.0 pp，openai3 T=10 时 +1.8 pp），T = ck 处没有差别。GPU 上必须用完整 256 项表：大 batch 时 M = 384 慢 38–44%，需要结构化 E8 距离计算才可能保住收益 |
| **V2 EVT-JHQ** | **NO-GO** | 在论文的 recall 目标上只少扫 3–7% 的候选；测试集上这些规则还掉了 0.06–0.18 pp。i.i.d. 极值公式严重失准。只有 openai3 在略低的 recall 目标处比降 nprobe 少扫 12–33%，属单数据集的局部发现 |
| **V3 RD-JHQ** | **NO-GO** | JL 旋转把残差方差拉平：按子空间分配的收益上限不到 1%，三个数据集中两个的最优分配就是均匀 8 bit。arxiv 上残差 MSE −2.4%，recall 无变化（验证与测试都是） |

**各版本的最佳 recall 与 QPS [GPU 实测]：** 都取 nprobe 128、论文 α。

| | B0 v65：recall / b=8 QPS / b=1000 QPS | V1 E8 原型：recall / b=8 / b=1000 | V2 | V3 |
|---|---|---|---|---|
| arxiv | 0.9766 / 16,659 / 220,089 | 0.9778 / 18,173 / 205,875 | 无 GPU 原型（离线 NO-GO） | 无 GPU 原型（离线 NO-GO） |
| vogue | 0.9643 / 19,140 / 236,493 | 0.9648 / 20,721 / 190,734 | 同上 | 同上 |
| openai3 | 0.9267 / 18,463 / 144,580 | 0.9271 / 19,937 / 89,935 | 同上 | 同上 |

V1 在 b = 8 时快约 8–9%，但这部分来自完整查表这条路径本身，与 E8 无关（见 2.5 节）。

**最值得继续的：V1（E8），但要满足两个条件：**
1. 实现结构化 E8 距离计算，用小表替代 256 项表，解决大 batch 下的查表代价；
2. 在同一个测速程序里确认“完整查表在小 batch 更快”这一旁证。

即便满足，收益上限也只是 recall 平台的小幅提高（np128 时 +0.04–0.13 pp），不是候选预算的大幅减少。

## 二、V1 E8-JHQ

### 2.1 核心数学思想

**JHQ 的码本：** JHQ 每个 8 维子空间的码本是立方体 {−c, +c}⁸。它是 8 个一维二值量化器的笛卡尔积，所以距离表可以拆成两张 16 项的表（16+16）。

**V1 的码本：** 换成 E8 格的 240 个根（第一壳层，8 维的最优接吻配置），加 16 个 ±2e_i，共 256 个码字。
- 每 8 维仍是 8 bit，不存任何每向量浮点量；
- 码字乘一个全局 scale，scale 只由训练向量拟合。

E8 格量化本身是成熟工具（Conway–Sloane；QuIP# 的 E8P 码本），这里不宣称发明。

### 2.2 源码修改

**离线** `v1_e8/implementation/`：
- `e8.py`：构造码本并核验；暴力编码器与结构化编码器，后者对三类码字各取最大内积，再按完整距离比较，因为范数不同；scale 拟合；按 JHQ 的流程重训残差。
- `eval_e8.py`：在论文索引的真实候选上评估。

**GPU 原型 `jhq_v68_e8/`**（从 v67 复制，v65 与 v67 不动）：
- 把 v47 起的 16+16 分解表换成每个子空间 256 项的完整表：`search.cu` 的建表 kernel、9 处扫描查表、退出界；
- 删掉只为分解表服务的笛卡尔性检查；
- `import_state` 改为直接接收码本。

**测速程序：** `examples/demo_jhq_v68_e8_bench.cu` 在同一进程、同一索引上并排测两种表示。
- A：论文索引走完整表；
- B：E8 走完整表；
- 导入前核对 list 布局。

**一致性检查：** A 与 B0 在同一 α 下 recall 完全相同（0.9766 / 0.9643 / 0.9267），说明完整表与分解表算出的距离一致。

### 2.3 正确性与理论预期 [离线实测]

- **码本：** 256 个码字两两不同，全部属于 E8，最小距离² = 2，关于原点对称。
- **编码器：** 结构化编码器与暴力编码器在高斯、t₃ 重尾、码字加噪声三类输入上距离完全一致。
- **最近 ≠ 最大内积：** 在 68.6% 的高斯样本上两者不同。
- **高斯源上的每维 MSE**（独立复现）：

| 码本 | 每维 MSE |
|---|---:|
| JHQ（c = 0.6745σ） | 0.3787 |
| 1-bit Lloyd–Max 立方体 | 0.3634 |
| E8 | **0.3195**（比 Lloyd–Max 低 12.1%） |

### 2.4 离线结果

| | primary MSE（E8 / JHQ） | 最终重建 MSE（E8 / JHQ 复现） | 固定 T 配对差（E8 − JHQ 复现，pp）：验证（校准 + 验证） | 测试集 |
|---|---:|---:|---|---|
| arxiv | 0.85 | 0.66 | 全部不显著 | 全部不显著 |
| vogue | 0.85 | 0.58 | T=80：+0.40 [−0.22, +1.02] | **T=80：+1.05 [+0.25, +1.85]**；T ≥ 160 不显著 |
| openai3 | 0.84 | 0.55 | **T=10：+0.75 [+0.05, +1.45]；T=20：+0.27 [+0.07, +0.47]** | **T=10：+1.85 [+0.95, +2.75]；T=20：+0.35 [+0.05, +0.65]**；T=40 不显著 |

**补充：**
- 按子空间单独定标反而更差，所以只用全局 scale。
- “只换 primary、仍用论文 D_H”的排序与 JHQ 几乎相同，说明收益主要来自更好的残差重建。

### 2.5 GPU 结果 [GPU 实测]

**(1) 完整 256 项表本身的代价**（A / B0，同一码、同一 α 与 nprobe，np128）：

| | b = 8 | b = 32 | b = 256 | b = 1000 |
|---|---:|---:|---:|---:|
| arxiv | ×1.09 | ×1.06 | ×1.11 | ×1.00 |
| vogue | ×1.08 | ×1.06 | ×1.00 | ×0.90 |
| openai3（M = 384） | ×1.08 | ×1.07 | ×0.75 | ×0.62 |

np512 时类似：openai3 在 b = 1000 时 ×0.56，vogue α 64 时 ×0.80。

- **小 batch：** 完整表放不进共享内存，只能走 L1/L2；几个查询的表全在缓存里，且每个子空间少一次查表。
- **大 batch：** 每查询 96 KB（M = 96）或 384 KB（M = 384）的表让 L2 抖动。仓库里 v59 的历史测量（factorised 在 M = 384 时快 +13–53%）方向一致。
- **注意：** A 与 B0 来自两个测速程序，计时范围相同，但交替测量的对象不同，小 batch 那 6–9% 可能有一部分来自测量环境。

**(2) E8 表示本身的作用**（B / A，同一程序、同一张表）：
- **np128：** recall +0.04–0.13 pp（openai3 在 α = 2 时 +0.30 pp），每一个配置都是正的；QPS 在 b = 8 时持平或快约 1%，b = 1000 时 arxiv −7%、vogue −10%、openai3 持平。
- **np512：** recall +0.07–0.45 pp；大 batch 时 arxiv 与 vogue 慢 4–13%。

**(3) 同 recall 下对 B0 前沿**（`GPU_COMPARISON.json`）：
- E8 把 np128 的 recall 平台抬高了 0.01–0.07 pp，超过 B0 在 np128 的最高 recall（arxiv 0.9777，vogue 0.9645，openai3 0.9267）。
- 在这条很窄的 recall 带内，B0 只能改用 np512 才能达到同样 recall，所以那里 E8 的吞吐是 B0 的 1.1–1.5 倍。
- 离开这条带，E8 在同 recall 下的差别就只剩完整查表路径本身的影响：小 batch 快约 8%；大 batch 时 arxiv 在 −24% 到 +2% 之间、vogue 在 −17% 到 +2% 之间、openai3 慢 37–44%。

### 2.6 是否符合理论

- **符合：** MSE 的降幅与格量化的理论方向一致（高斯上 −12%，真实数据 −15–21%）；残差因此变得更精确。
- **不符合（与 rank-optimal 研究的结论相同）：** MSE 降低没有转化为近邻排序的改善。recall 平台本来就接近全 IVF 上限，可提升的空间只有 0.1 pp 量级；小预算处的收益只在两个数据集上出现。

## 三、V2 EVT-JHQ

### 3.1 核心数学思想

**极值公式：** 若一个 list 内候选距离 i.i.d.，则 P(min D < τ) = 1 − (1 − F(τ))ⁿ，其规范化极限为 GEV 分布。

**做法：** 先扫最近的 L1 个 list 得到 top-ck 门限 τ；之后每 16 个 list 为一个阶段，风险低于 ε 的 list 不读。风险只用读 list 之前就有的量：τ、查询到 list 中心的距离、list 大小、名次。

**比较对象：** 四种风险模型——全局分箱、i.i.d. 极值公式、按大小分档的 GEV、校准后的逻辑回归。

### 3.2 源码

`v2_evt/implementation/evt_sim.py`：在论文索引的真实探查候选上做离线模拟。没有做 GPU 原型，原因见 3.4。

### 3.3 结果 [离线实测]

| | oracle（只扫含 top-ck 的 list） | 验证集“不损失 recall”的最好规则 | 同一规则在测试集上 |
|---|---|---|---|
| arxiv | 81% 的候选 | 96.3%，recall 不变 | 94.9%，recall −0.18 pp |
| vogue | 61% | 96.9%，不变 | 96.6%，−0.06 pp |
| openai3 | 12% | 93.0%，不变 | 92.0%，−0.10 pp |

**允许损失 recall 时，与降 nprobe 比（验证集）：**
- arxiv 不如降 nprobe；
- vogue 少扫约 5%；
- openai3 在 recall 低 0.25–2 pp 时少扫 12–33%（`figures/fig2_evt_frontier.png`）。

**概率校准：**
- i.i.d. 公式在 arxiv 上预测 0.1–1% 的 list，实际有 33% 含有更好的候选；
- GEV 同样失准；
- 只有逻辑回归接近对角线。

### 3.4 为什么失败

1. **候选不是 i.i.d. 样本。** 同一 list 的成员共享位置，到查询的距离强相关，所以 i.i.d. 极值公式和 GEV 都失准。
2. **可用特征不够。** 读之前能拿到的量区分不了“含不含 top-ck 候选”，离 oracle 很远。
3. **GPU 收益不够。** primary 扫描占端到端 41–65%（B0 的 nsys 分阶段时间），少扫 3–7% 最多对应约 4% 的端到端收益；多阶段扫描还要在阶段之间同步。达不到 10% 的参考门槛，所以没有做 GPU 原型 [推导]。

## 四、V3 RD-JHQ

### 4.1 核心数学思想

在 Σ 8·b_m = 8d 的约束下，按率失真理论给各子空间分配残差位数（b ∈ {6, …, 10}）。高斯反向注水只作参考，实际用实测的失真–码率曲线做贪心整数分配，另做查询加权分配。反向注水是经典工具。

### 4.2 源码

`v3_rd/implementation/rd.py`：
- 每个子空间按 2^b 级重训码本；
- 码按真实变位宽打包，每向量 d 字节；向量化解码；往返测试逐位一致；
- 在候选上评估。

### 4.3 结果 [离线实测]

| | 残差方差变异系数（按维 / 按子空间） | 注水收益上限（按维 / 按子空间） | 最优整数分配 | 残差 MSE | recall |
|---|---|---|---|---|---|
| arxiv | 0.25 / 0.087 | −2.6% / −0.4% | 7 个 7 bit、82 个 8 bit、7 个 9 bit | −2.4% | 验证与测试都无差别（配对差 −0.02 pp，CI 含 0） |
| vogue | 0.34 / 0.137 | −4.3% / −0.9% | 全部 8 bit | 0 | 与均匀分配逐位相同 |
| openai3 | 0.12 / 0.041 | −0.7% / −0.1% | 全部 8 bit | 0 | 同上 |

**正确性旁证：** 均匀分配走变位宽链路，与 JHQ 离线复现的残差 MSE 逐位相同（2.8308e-5 / 4.1313e-5）。

### 4.4 为什么失败

- **前提不存在：** 码率分配要求方差不均，JL 随机旋转恰好把方差摊平了。SAQ 能从分配中获益，是因为它先做 PCA。
- **收益更小：** 每多 1 bit，失真只降到约 1/2，不是高码率理论的 1/4。
- **解码更慢：** 变位宽解码要跨字节提取，比按字节读慢。没有质量收益时不值得做 GPU 原型。

## 六、新颖性

详见 NOVELTY_AUDIT.md。三者都不构成算法创新：
- **E8：** 是已有工具的直接应用，最接近的是 QuIP# 的 E8P 码本。本研究的贡献只是测量：格码本的 MSE 增益在 JHQ 的两级结构里几乎不转化为排序收益，以及失去 16+16 分解在不同 batch 下的代价。
- **EVT 剪枝：** 是学习式提前终止（Li 等 SIGMOD 2020）、ConANN、CLIP 等已有路线的简单变体；极值公式在真实数据上不成立。
- **RD：** 是经典工具；JL 旋转之后，它的前提已经不存在。

## 七、下一步

1. **如果继续 V1：**
   - 先实现结构化 E8 距离：类 2 的码字可以按前后 4 维拆成两张 16 项表，类 1、类 3 只需 ±q_i 小表，再加一张 256 项的解码表放在常量内存；
   - 确认大 batch 下的查表代价能否消掉；
   - 再在六个数据集上看 recall 平台的提高是否普遍。
2. **完整查表在小 batch 更快（6–9%）这一旁证：** 这是 kernel 层面的现象，不是算法创新。需要在同一测速程序内对照确认后，才能考虑按 batch 大小选择查表方式。
3. **V2、V3 不建议继续。**

**提交：** 见 git log（`exp/math-algorithm-ablation`）。复现见 REPRODUCE.md，过程见 EXPERIMENT_LOG.md。
