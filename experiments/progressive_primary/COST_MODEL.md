# 阶段成本模型：Progressive Primary Screening 对比 α 优化后的 v65（b = 8 / 1000）

由 `cost_model.py` 生成：数值在 `cost_model.json`，逐配置表在 `COST_MODEL_TABLE.csv`，图为 `figures/fig3_gpu_cost_breakdown.png`。

**本文件没有任何数字来自新的 GPU kernel。** 离线门槛未通过，按 brief 不进入 CUDA 原型。各项来源标记如下：

| 标记 | 含义 |
|---|---|
| **[M]** | 实测：pipeline campaign 的 nsys GPU 时间（`../pipeline_campaign/exp2`），RTX 5090。<br>• 原始 α 下的 v63 构建：b=8 时 G=8 加共享界，就是 v65 在 b=8 的执行；b=1000 时 G=0，同 v65。<br>• 降低 α 的 v62 扫描：给出 scan、merge、refine、top-k 随 ck 的变化（b=8 G=8，b=1000 G=0）。 |
| **[D]** | 推导：把实测曲线换到别的候选数上取值，或按离线 pilot 实测的字节比例缩放 |
| **[T]** | 理论：明确写出的假设 |

## 1. 基线：α 优化后的 v65（v65@T*）

v65 在 ck 的实测阶段时间，换算到 T* 后作为基线 [M→D]：
- scan、merge、refine、top-k 各自在降 α 曲线上按 log(c) 插值；
- 再按 v65 在 ck 处的实测值归一化。

| workload | ck → T* | b=8：v65 实测 / v65@T*（µs） | b=1000：v65 实测 / v65@T*（µs） |
|---|---|---:|---:|
| arxiv-768 α100 | 1000 → 750 | 480.1 / 446.8 | 4555.8 / 4380.8 |
| vogue-768 α64 | 640 → 640 | 421.6 / 421.6 | 4611.0 / 4611.0 |
| openai3-3072 α4 | 40 → 30 | 433.0 / 432.2 | 6982.2 / 6972.3 |

T* 由本轮 validation 重新选出，结果与上一轮 Local-First 相同。

## 2. 模型结构

把 v65 在 ck 的扫描时间拆成 A + S(ck)：
- **A** [D]：降 α 曲线上最小 ck 处的扫描时间。它包括读取、查表和每个候选的固定开销，这部分随读取的 word 比例缩小。
- **S(c)** [D]：选择缓冲区随 c 增大而增加的时间。threshold compaction、bitonic 排序和更大的 shared memory 都算在里面。

Progressive 的各阶段：

| 阶段 | 模型 | 标记 |
|---|---|---|
| Stage 1 部分扫描 | A·(f·s1 + 1 − f)。s1 = 离线实测的 Stage 1 sector 比例（≈ p） | [D] |
| Global Top-L 选择 | S(L)，L 是全局保留数；b=8 时另加分组合并 merge(L) | [D]，超出实测范围时外推 |
| Stage 2 剩余主码 | 两项相加：<br>• 散乱读取：s2·B_old_sec·b / (1.79 TB/s · eff)，s2 = 离线实测的 32 B sector 比例；<br>• 查表：A·f·(L/n)·(1−p)。<br>和取启动下限之后的较大值 | [T]、[D] |
| Stage 2 选 T* | 按 v65 最终 top-k kernel 在 L 个候选上的时间计价（它只选 10 个，偏乐观） | [D] |
| μ 元数据 + top-L scratch | 离线实测的字节数，按 1.79 TB/s · eff 计 | [T] |
| 前端、refine、final top-k、host | 与 v65@T* 相同，互相抵消 | [M→D] |

三种情景：

| 情景 | f（随 p 缩小的扫描比例） | S(L)、merge(L) 超出实测范围时 | 散乱 sector 带宽 | Stage 2 下限 |
|---|---|---|---|---|
| **U** 上限 | 1 | 取 S(T*)、merge(T*)，即 Top-L 免费 | 峰值 | 0 |
| **O** 乐观 | 1 | 按最后两点在 log(c) 上外推（次线性） | 峰值 | 3 µs |
| **C** 中性 | 0.8 | 按 c 线性外推。若本数据集曲线是平的，不低于 arxiv 实测的每候选增长：arxiv 的实测范围最宽，而 openai3 只测到 ck=10–40 | 峰值的 50% | 5 µs |

**关于 C 情景的外推：** arxiv 和 vogue 需要 L = 5120–16000，远超实测的 ck ≤ 2000。线性外推得到的大负数（−70% 到 −280%）只说明 Top-L 选择会主导成本，不能当作点预测。结论应以 **U（上限）**为准：如果连 U 都不到 10%，门槛就稳健地不通过。

## 3. 结果：validation 选出的工作点

表中数值为预测的端到端**时间节省**，吞吐提升 = 1/(1−节省) − 1。

工作点按 brief 第 9 节的预设规则，即按理想字节在 validation 上选出。另列“按真实字节”的第二规则：它是看到第一轮结果后补充的，单独标明。

### 3.1 arxiv-768（T* = 750）

| 规则 | 策略 | p / L | test 非劣 | b=8：U / O / C | b=1000：U / O / C |
|---|---|---|---|---|---|
| 预设（理想字节） | A0 | 0.5 / 8ck | ✓ | +7.7% / −25% / −72% | +1.7% / −43% / −125% |
| 预设 | A1c | 0.25 / 16ck | ✓ | +8.7% / −34% / −155% | −14.5% / −73% / −276% |
| 预设 | A2 | 0.5 / 8ck | ✓ | +7.6% / −25% / −72% | +0.7% / −44% / −127% |
| 第二规则（真实字节） | 其余策略 | 0.5–0.75 / 2–4ck | ✗（test 非劣不成立） | — | — |

**任何非劣工作点在 U 上限下都不到 10%。**

### 3.2 vogue-768（T* = 640）

| 规则 | 策略 | p / L | test 非劣 | b=8：U / O / C | b=1000：U / O / C |
|---|---|---|---|---|---|
| 两种规则 | A2 | 0.5 / 8ck | ✓ | +10.2% / −9.5% / −104% | +12.4% / +4.0% / −74% |

- 只有 Top-L 免费、散乱读取达到峰值带宽的 U 上限超过 10%。
- O 情景在 b=1000 为 +4–5%，b=8 为负。

### 3.3 openai3-3072（T* = 30）

| 规则 | 策略 | p / L | test 非劣 | b=8：U / O / C | b=1000：U / O / C |
|---|---|---|---|---|---|
| 预设（理想字节） | A0 | 0.125 / 32ck | ✓ | +27.5% / +27.1% / +6.0% | +32.4% / +32.3% / −5.8% |
| 预设 | A1 | 0.125 / 32ck | ✓ | +27.5% / +27.2% / +6.1% | +32.8% / +32.7% / −4.8% |
| 第二规则（真实字节） | A0 | 0.25 / 16ck | ✓ | +24.9% / +24.6% / +12.0% | +35.8% / +35.7% / +13.8% |
| 第二规则 | A1 | 0.25 / 8ck | ✓ | +25.9% / +25.7% / +16.6% | +40.0% / +40.0% / +24.3% |

A1 在第二规则下的 C 情景 +16.6% / +24.3%，对应吞吐 ×1.20 / ×1.32。

openai3 是唯一在 O、C 情景下预测收益超过 10% 的工作负载，但有两点保留：
- 预设规则下，A0（固定前缀）与 query-aware 策略打平。
- 第二规则下 A1 比 A0 多出的部分（C 情景多 4.6 / 10.5 个百分点），来自它把 L 从 16·ck 降到 8·ck，即 Top-L 选择更便宜。

**多数收益来自 progressive 结构本身，也就是 v21 的前缀 cascade 机制加上全局 Top-L。**

另外，openai3 的选择曲线只测到 ck = 40，而 L = 320–1280，外推跨度达 3–5 个倍数。C 情景借用了 arxiv 的增长斜率，这一项的不确定性最大。

### 3.4 test 上挑出的包络

`cost_model.json` 里的 `envelope` 给出每个策略在所有 test 非劣配置中的最好值。它是在 test 上挑选的，只作乐观包络，不作决策依据，结论不变：
- **arxiv：** O 情景最好 −7%（A0，p=0.75，L=2ck，b=1000）；
- **vogue：** O 情景最好 +8.3%（A3，p=0.75，L=2ck，b=1000）；
- **openai3：** O 情景 +40%（A0 与 A1 都是 p=0.25，L=8ck）。

## 4. 成本由什么决定

1. **全局 Top-L 选择**
   - 在 768 维数据集上，非劣需要 L = 8·ck（5120–8000，占候选的 11–17%），A1c 甚至要 16·ck。
   - v65 的选择代价随 ck 增长：arxiv 在 b=1000 时从 ck=1000 到 2000 增加约 595 µs [M]；b=8 的分组 merge 从 13 µs 增至 39 µs [M]。
   - 把 L 扩大 8–16 倍，这一项就足以抵消 Stage 1 的节省。
2. **Stage 2 的散乱读取**
   - 每个候选在每个未读 word 行上各占一个 32 B sector，相邻被选中的候选共享 sector 能部分抵消。
   - 相对理想的 4 B/word，实测放大 2.5–5.4 倍：arxiv A0 为 3.9×，vogue A1 为 4.6×，openai3 A1 为 5.4×。
   - 在 arxiv p=0.5、L=8ck 时，Stage 2 的 sector 流量是 B_old 的 33%，而 Stage 1 只省下 50%。
3. **μ 元数据与 scratch：** 只占 B_old 的 2–5%，不是决定因素。
4. **v65 的分组扫描在 b=8 时受并行度限制。**
   - 扫描 A 只有 150–180 µs，前端、refine、top-k 和 host 已占端到端的 45–58% [M]。
   - Stage 1 节省的上限是 A·(1−p)：p=0.5 时约 75–90 µs，openai3 在 p=0.25 时约 134 µs。

## 5. 没有建模的部分（都会让真实结果更差或更不确定）

- **更大选择缓冲区对 occupancy 的影响：** 超出实测曲线范围的部分没有计入。NEGATIVES 记录过，每块多 16 KB shared memory 会损失 17–26%。
- **Stage 2 的跨查询 L2 复用：** 未计入，对 progressive 有利。
- **L2 命中：** 散乱 sector 按 DRAM 计价（50% 或 100% 峰值），没有区分 L2 命中。QDUP 显示 nprobe=128 时，L2 已经服务大部分重复读取，所以 v65 自身的扫描也未必受 DRAM 限制。
- **fp32 求和顺序：** Stage 1 部分和加 Stage 2 余项，与一次性求和的 fp32 舍入不同，近似并列的候选可能交换。离线全部用 FP64。
- **Nsight Compute 计数器：** 本机为 ERR_NVGPUCTRPERM，不可用；HBM/L2 实际流量没有任何硬件计数器证据。
