# JHQ-CPU 残差精排的 list 分组：实现与实测

| 项目 | 内容 |
|---|---|
| 仓库 | `jiabhan/JHQ`，基于 `1636e19`；本地分支 `opt/list-grouped-refine`（未推送到任何远端） |
| 机器 | AutoDL，Xeon Platinum 8470Q；容器 CPU 配额 25 核；宿主机与其他租户共享，测试期间负载 11–21 |
| 编译 | g++-12，`-O3 -DNDEBUG -mavx2 -mno-avx512* -include immintrin.h`（与之前服务器上的构建相同）；faiss `5702caf` |
| 数据 | vogue-768：932,328 条 base，1000 条查询；IndexFlatL2 粗量化，nlist 1024，M 96，level_bits [8,4]（每条 480 B），JL 旋转，用前 30 万条训练 |
| 对照 | 原版库 = `108cefb`（`1636e19` 加编译修补和基准程序，精排代码未动）；优化版 = 本分支 |

## 结论

1. **结果逐位不变。**
   - 在三种存储、两个入口、store_pairs、无效 probe、L2 与 IP 下，所有模式的标签和距离都与原实现逐位相同：
     - 2268 次计时运行；
     - 81 项 `search_preassigned` 检查；
     - 54 项 IP 检查；
     - 40 个进程的跨二进制哈希比较。
   - 原因：并列的处理方式靠"精排结果按候选原位置存放、再按原顺序进堆"来保证，不依赖碰巧。
2. **精排阶段的收益只出现在按 list 预解码的存储上，而且要求 T 较大。**
   - 在 list 内按 offset 升序时（自动模式所用的变体），T = 400 快 1.04–1.14 倍，T = 1000 快 1.11–1.20 倍，T = 2000 快 1.15–1.26 倍。
   - T = 100 时 1.00–1.03 倍。T = 20 时 0.94–1.07 倍，多数配置略慢，约每个查询多 1 µs。
   - separated 存储为 0.99–1.05 倍，packed 存储为 0.99–1.02 倍，与噪声无法区分。
3. **端到端收益很小。** 主阶段（全部 probe list 的 primary 距离和全局 top-T）占单查询延迟的比例是：预解码 74–98%、separated 67–98%、packed 36–97%。精排的占比相应为 0.2–22%、0.2–29%、0.9–63%，但分组对 packed 无效。
   - 同一进程内交错比较：预解码存储在 T ≥ 1000 时端到端快 0.7–5.5%；T ≤ 400 时，以及 separated 和 packed 的全部配置，都在 ±1.2% 内。
   - 和原版二进制按进程交错比较（正式版构建，不带计时）：自动模式的批量 QPS 为原版的 1.00–1.04 倍（预解码）和 1.005–1.01 倍（packed）。
4. **自适应回退。** T < 256 时走原来的逐个候选循环，T ≥ 256 时分组并按 offset 升序，这两个默认值都来自上面的数据。
5. **一个必须避免的回退：计时插桩。**
   - 每个查询读两次时钟，使批量 QPS 下降 2–4%。这一点由三方进程级对照确认。
   - 因此计时和计数只在 `JHQ_REFINE_PROFILE=ON` 的构建中编入，默认关闭。
6. **剩余瓶颈**（第六节）：
   - 主阶段的 primary 扫描；
   - packed 路径每个候选的位解码和 `std::vector` 分配（每个候选 4.7–7 µs，是预解码路径的 5 倍）；
   - 预解码两级残差走的是标量循环；
   - separated 存储按全局 id 存放，没有 list 局部性可用。

## 一、原实现与问题

`search_preassigned()` 和 `search_preassigned_with_rotated_queries()` 的全局两阶段路径：
1. 对全部 probe list 计算 primary 距离，用最大堆保留全局 top-T（T = max(k, ⌈αk⌉)），然后按距离排序；
2. 按 primary 顺序逐个精排。每个候选都要：
   - 解出 list_no 和 offset；
   - 调用 `invlists->list_size()`；
   - 调用 `scanner->set_list(list_no, 0)`；
   - 构造 `ScopedCodes` 和 `ScopedIds`；
   - 调用 `refine_distance_from_primary_for_list()`，结果以严格比较推入 top-k 堆。

**读代码确认的三条存储路径：**

| 存储 | 何时使用 | 精排时读什么 | list 局部性 |
|---|---|---|---|
| separated | 在进程内 add 后（读回的索引会清掉） | 用 `list_to_global_mapping[list][offset]` 找到全局 id，再读全局数组里的残差码和 cross term | 无：数据按全局 id 存放 |
| 按 list 预解码 | 读回后 list 长度 ≥ `pre_decode_threshold`（默认 1000） | 该 list 的预解码数组 | 有 |
| packed | 其余情况，或 `enable_pre_decoded_codes(false)` | 位解码整条码，重算完整距离；每次调用分配一个 `std::vector` | 有，但被解码成本淹没 |

**`set_list` 的成本：** 只是设置 `list_no` 并查一次预解码指针；`ScopedCodes`/`ScopedIds` 对 ArrayInvertedLists 只是取指针。所以逐个候选的固定开销本来就不大，事先就预计分组不一定更快。

## 二、实现（`jhq/jhqlib/impl/IndexIVFJHQSearch.cpp`）

两个入口原本有完全相同的精排循环。现在都调用同一个 `refine_global_candidates()`（noinline），由它选择路径：
- **`refine_one_at_a_time`**：原循环逐字保留（只把推堆的几行提成了 `push_refined`），作为回退和 `refine_grouping = 0`。
- **`refine_grouped`**（`refine_grouping = 1`；取 2 时再按 offset 升序）：
  1. **分组，O(T + nprobe)。**
     - 用一个开放寻址表（容量为 2 的幂且 ≥ 2·min(T, nprobe)，每个查询清零 O(nprobe)），把 list_no 映射到组号，组号按首次出现的顺序分配；
     - 再做一次稳定的计数排序，得到"按组排列的候选下标"。
     - 不对 T 个候选做全局排序，也不做 O(nlist) 的初始化。
     - 无效 list 的候选标记后跳过，与原循环相同。
  2. **组内 offset 升序（模式 2）。** 每组 ≤ 32 个时用插入排序，否则用 `std::sort`，比较键为 (offset, 候选下标)，结果确定。
  3. **逐组精排。**
     - 每组取一次 `list_size`；
     - 如果组内没有一个 offset 落在 list 内，这个 list 就不打开（原循环也不会为它调用 `set_list`）；
     - 否则调用一次 `set_list`，构造一次 `ScopedCodes`、一次 `ScopedIds`，它们的 RAII 作用域就是这一组；
     - 距离和 id 写进按候选原位置索引的数组。
  4. **最后按原候选顺序推入 top-k 堆。** 推入的值、次数和顺序都与原循环相同，所以并列的结果也相同。
- **scratch：** 每个线程一份 `thread_local`，跨查询、跨搜索调用复用，没有逐候选的分配。

**其他改动：**
- `IndexIVFJHQ.h`：
  - 新增 `refine_grouping`（−1 自动，0 原循环，1 分组，2 分组且 offset 升序）和 `refine_grouping_min_candidates`（默认 256），不写入索引文件；
  - `IndexIVFJHQStats` 增加精排计数与分阶段时间，只在 `JHQ_REFINE_PROFILE` 构建中填写。
- `IndexIVFJHQIO.cpp`：统计的 `add()`。
- `jhqlib/CMakeLists.txt`：新增 `JHQ_REFINE_PROFILE` 选项，默认 OFF。

**没有改动：**
- JL 变换、量化、primary 距离；
- top-T 的选择；
- scanner 里的残差距离公式和每个候选内部的累加顺序；
- 搜索参数的含义、索引格式、L2/IP 语义、store_pairs、OpenMP 并行方式、无效 list 的处理；
- 任何 GPU 代码。

**另外一个 commit 里的编译修补**（与之前服务器上的 `JHQ_patched` 构建相同，和优化无关，原版和优化版都包含）：
- faiss `5702caf` 把 6 参数的 `scan_codes` 改成了非虚函数，所以 scanner 头文件里去掉两处 `override`；
- cblas 头文件的 include 逻辑；
- 补 `immintrin.h`；
- examples 改为链接 `jhq` target。

## 四、性能（同一进程内交错，配对比值）

**测法：**
- 每个配置先跑一轮不计时的预热，然后跑 7 轮，每轮轮换模式的先后；
- 精排时间来自 `JHQ_REFINE_PROFILE` 构建：线程时间按查询平均；
- 提速 = 同一轮内模式 0 与模式 2 的比值，取 7 轮的中位数，方括号内是逐轮比值的范围。
- 批量：1000 条查询一次调用，16 线程；单查询：100 条查询逐条调用，1 线程。
- 下表都是 nprobe = 32；nprobe 为 8 和 128 时的数据见 `results/full/tables.md`，趋势相同。

**单查询，精排阶段（µs/查询，模式 0 → 模式 2）与端到端延迟：**

| 存储 | T（k, α） | 打开的 list 数 | 精排 | 提速 | 端到端 µs | 端到端提速 |
|---|---|---:|---|---|---|---|
| 预解码 | 20（10, 2） | 5.9 | 20.8 → 21.9 | 0.94 [0.90, 1.15] | 7631 → 7660 | 1.000 |
| 预解码 | 100（10, 10） | 13.5 | 95.2 → 94.8 | 1.00 [1.00, 1.02] | 7584 → 7563 | 1.001 |
| 预解码 | 400（10, 40） | 20.1 | 373 → 342 | 1.08 [1.04, 1.56] | 7360 → 7372 | 0.998 |
| 预解码 | 400（100, 4） | 20.1 | 402 → 358 | 1.13 [1.11, 1.14] | 8196 → 8105 | 1.011 |
| 预解码 | 1000（10, 100） | 22.9 | 968 → 819 | 1.17 [1.16, 1.20] | 8981 → 8811 | 1.023 |
| 预解码 | 2000（100, 20） | 23.7 | 1913 → 1527 | 1.24 [1.21, 1.31] | 10402 → 10008 | 1.042 |
| separated | 20 / 100 / 400 / 400 / 1000 / 2000 | 同上 | 24 → 24 … 1935 → 1918 | 1.04 / 1.00 / 0.99 / 1.02 / 1.00 / 1.01 | ±1% | 0.994–1.007 |
| packed | 同上 | 同上 | 128 → 129 … 9504 → 9429 | 1.00 / 1.00 / 1.00 / 1.01 / 1.01 / 1.00 | ±1% | 0.994–1.006 |

**批量（16 线程）：**
- 预解码：精排提速 0.98（T = 20）、1.02（T = 100）、1.10 和 1.12（T = 400）、1.17（T = 1000）、1.21（T = 2000）；QPS 提升 0.996–1.032，只有 T ≥ 1000 时为 +2.5% 和 +3.2%。
- separated：精排 1.00–1.03，QPS 0.998–1.004。
- packed：精排 0.996–1.007，QPS 0.994–1.008。

**全部 nprobe 汇总（预解码，模式 2 的精排提速范围）：**

| T | 单查询 | 批量 |
|---|---|---|
| 20 | 0.94–1.07 | 0.95–0.99 |
| 100 | 1.00–1.01 | 1.00–1.03 |
| 400 | 1.04–1.14 | 1.07–1.12 |
| 1000 | 1.15–1.20 | 1.11–1.17 |
| 2000 | 1.20–1.26 | 1.15–1.21 |

模式 1（只分组、不排序）在 T ≥ 400 时的提速是 0.98–1.16，总体不如模式 2，所以自动模式选模式 2。

**`set_list` 与 scoped 访问次数（每个查询）：** 原循环中都等于 T；分组后等于有候选的 list 数：
- nprobe 8：4.0–6.3；
- nprobe 32：5.9–23.7；
- nprobe 128：6.5–70.6。

例如 T = 2000、nprobe 32 时，2000 次降到 23.7 次。

**为什么只有预解码有收益：** 每个候选的精排成本是：
- 预解码 0.8–1.3 µs；
- separated 1.0–1.5 µs；
- packed 4.7–7.3 µs。

省掉的 `set_list`、`list_size` 和两次 scoped 访问只有几十纳秒。预解码的收益主要来自访存局部性：同一 list 的残差码连续存放，按 offset 升序访问时是单向前进的地址流。separated 存储按全局 id 存放，packed 的成本几乎全在位解码，所以这两种存储都拿不到这部分收益。

## 五、与原版二进制的对照（进程级交错）

不同二进制只能在不同进程里比较，所以按 ABBA 或 ABC-CBA 的顺序轮换进程，以抵消机器状态的漂移。

**第一轮：原版 vs 优化版（带计时）**，`results/ab/`：
- 批量模式下，优化版即使走原循环（模式 0），QPS 也只有原版的 0.94–0.98（预解码）和 0.97–1.00（packed）；
- 单查询的波动有 ±10%，看不出差别。
- 模式 0 的逻辑与原版相同，所以差别只可能来自插桩或代码生成。

**第二轮：原版 vs 优化版不带计时 vs 优化版带计时**，`results/ab3/`，批量，nprobe 32，各 4 个进程。表中是对原版的 QPS 比值，方括号内为范围：

| 存储 | T | 不带计时，模式 0 | 不带计时，自动 | 带计时，模式 0 | 带计时，自动 |
|---|---|---|---|---|---|
| 预解码 | 20 | 1.018 [1.00, 1.05] | 1.021 [0.97, 1.05] | 0.974 | 0.972 |
| 预解码 | 100 | 0.994 [0.98, 1.03] | 1.000 [0.98, 1.02] | 0.961 | 0.963 |
| 预解码 | 1000 | 1.012 [1.01, 1.02] | 1.020 [0.99, 1.03] | 0.961 | 0.982 |
| 预解码 | 2000 | 1.011 [1.01, 1.02] | 1.041 [1.00, 1.05] | 0.973 | 1.013 |
| packed | 20 | 0.995 | 1.012 | 0.966 | 0.981 |
| packed | 100 | 0.989 | 1.005 | 0.960 | 0.961 |
| packed | 1000 | 1.008 | 1.009 | 0.991 | 0.984 |
| packed | 2000 | 0.999 | 1.010 | 0.996 | 0.996 |

**结论：**
- 不带计时时，优化版的原循环与原版一致（0.99–1.02），自动模式为 1.00–1.04。
- 带计时会让批量 QPS 下降 2–4%。可能的原因是这台机器上读时钟的代价较高，但没有进一步验证。
- 所以计时默认关闭。第四节的模式比较都在同一个带计时的二进制里进行，各模式承担相同的计时开销，比较结论不受影响。

## 六、剩余瓶颈

1. **主阶段（primary 扫描 + 全局 top-T）占单查询延迟的 67–98%**（packed 在 T 很大时降到 36%，因为那时精排更贵）。
   - 单线程每个查询 4–16 ms（nprobe 8–128）：每个被 probe 的向量做 M = 96 次查表，再维护 T 大小的堆。
   - 精排上的任何优化，收益上限就是精排所占的比例：预解码 0.2–22%，separated 0.2–29%，packed 0.9–63%。
2. **packed 精排：每个候选 4.7–7.3 µs，是预解码的 5 倍。**
   - `distance_to_code_with_bit_decoding` 逐位解出 96 + 768 个字段，每次调用分配一个 `std::vector`，还要从码本重算 cross term。
   - 分组对此无效。要改善，需要预解码（默认对长度 ≥ 1000 的 list 开启）或改这个函数，后者超出了本次的范围。
3. **预解码的两级残差走标量循环。** `compute_residual_distance_pre_decoded` 在 `num_levels == 2` 且有 residual PQ 的分支里，用 768 次依次累加的查表，而另一个分支有 AVX2/AVX-512 gather。这是每个候选约 0.9 µs 的主要来源。
4. **separated 存储：** 每个候选要查一次 `list_to_global_mapping[list][offset]`（vector 的 vector），残差码和 cross term 按全局 id 随机访问。除非改成按 list 排列，分组无法改善。
5. **其他部分**（粗量化搜索、旋转、最终堆）占 1.2–5.6%。
6. **测量本身的限制：**
   - 宿主机是共享的，单查询延迟逐轮波动的中位数为 3–5%，最大 20%；
   - 所以单查询端到端小于 ±2% 的差别不能当真，结论以同进程配对比值和进程级交错为准。

## 七、内存

- scratch 是每个线程一份 `thread_local`，大小按历史最大值保留；
- 每个候选约 21 B（下标、组号、距离、id、标记），哈希表每个槽 12 B，每个组 24 B；
- 实测最大值是每线程 47.5 KB（T = 2000，nprobe 128），16 线程合计约 0.76 MB；
- 自动模式在 T < 256 时不分配。

**正式版冒烟测试（`9bd9990`，默认构建，不带计时）：**
- 范围：预解码与 packed 两种存储，k:α 取 10:2、10:40、100:20，nprobe 取 8、128，批量与单查询，模式 0、1、2、−1；
- 结果：96 次运行与 72 项检查全部逐位一致；默认构建下统计字段全为 0，说明插桩确实没有编入。原始输出在 `results/final/`。

## 八、复现

```sh
# 服务器上，/root/autodl-tmp/JHQ_lgr 为 jiabhan/JHQ 的克隆，已 fetch 本分支；jhq/external/faiss 为 faiss 5702caf
bash build_box.sh 108cefb <本分支 commit>   # PROFILE=ON 构建原版与优化版
bash run_box.sh /root/autodl-tmp/lgr/full    # 建索引（一次），三种存储 × 网格 × 7 轮；原版 3 轮；IP 检查
python3 analyze.py results/full --md results/full/tables.md
bash ab_box.sh <dir> <优化版二进制>          # 原版对优化版的进程级 ABBA
bash ab3_box.sh <dir> 2 ref=... noprof=... prof=...
python3 analyze_ab.py results/ab; python3 analyze_ab3.py results/ab3 3
```

**数据位置：** 索引（464 MB）在服务器的 `/root/autodl-tmp/lgr/index/`，没有入库。

**环境说明：** 容器 CPU 配额为 25 核，所以批量用 16 线程；BLAS 为单线程（`OPENBLAS_NUM_THREADS=1`）。
