# Per-query adaptive refinement：oracle gap（2026-10-12）

复现命令：`python3 experiments/perquery_oracle/oracle_gap.py`（纯 CPU，几秒），完整输出见 `out_oracle_gap.txt`。

本分析只用现有数据，没有重新搜索：
- `alpha_perquery/`：每条查询在每个 α 下的 top-10 id，GPU v57 生成；
- `budget_arms_2ds.log` 和 `budget_arms.log`：各固定 α 的实测 QPS；
- `k_and_stages.log`：α=4、16、100 时各 stage 的实测耗时。

## 问题

在同一个 workload 里，不同查询需要的精排预算是否差别很大？如果每条查询都恰好拿到它需要的 α，相比最好的单一 workload 级 α 能省多少？

## 方法

- 两个 oracle 都允许逐查询看答案：一个看 α_max 的输出（不需要标签），一个看 ground truth。在线方法拿不到这些信息，所以这里算出的是上界。
- 时间模型：查询在 α 下的耗时 T(α) 取同一 α 的整批运行中每条查询的平均耗时（1/QPS），并做单调（isotonic）平滑去掉测量噪声；混合 batch 的耗时取其中各条查询 T 的平均。
- 这个模型是最理想的情况：没有慢 block 造成的拖尾，没有调度开销，预测器完美且不花时间，scan 阶段的 top-ck 也按每条查询各自的 ck 缩小。
- 质量对齐：per-query oracle 与 workload 级 α 在同一约束下比较：
  - LF10：同一批 1000 条查询上，与 α_max 输出不一致的槽位 ≤10 个（共 10000 个槽位）。这蕴含相对 α_max 的 recall 损失 ≤1e-3。
  - GT10：丢失的真近邻 ≤10 个。
  - 两种约束下，per-query 的分配都用精确的多选背包求解。

## 结果

**A. 需求差异：** vogue 上差异很大，openai3 上几乎没有。下表是"与 α_max 输出完全一致"所需最小 α 的累积分布：

| | ≤2 | ≤4 | ≤8 | ≤16 | ≤32 | ≤64 |
|---|---:|---:|---:|---:|---:|---:|
| vogue/128 | 29% | 53% | 75% | 91% | 97.3% | 99.6% |
| openai3/128 | 92% | 99.9% | 100% | | | |

vogue 的 workload 级 α=64 是由大约 3% 的难查询决定的。

**B. 质量对齐下 per-query oracle 相对 workload 级 α 的上界：**

| 配置 | workload α | 精排候选减少 | 理想时间加速（主 QPS / 备用 QPS） | 天花板：所有查询都用 α=2 |
|---|---:|---:|---:|---:|
| vogue/128 | 64 | −86% | ×1.33 / ×1.38 | ×1.37 |
| vogue/512 | 64 | −85% | ×1.14 / ×1.17 | ×1.15 |
| openai3/128 | 4 | −46% | ×1.00 / ×1.01 | ×1.00 |
| openai3/512 | 4 | −46% | ×1.01 / ×1.00 | ×1.01 |

候选数大幅减少，但时间收益要小得多，因为 α 无关的部分（粗筛加主码 scan）占了大头。vogue/128 在 α=64 时，与 α 有关的时间只占 27%。

**C. 论文全部 12 个配置的天花板**：用 `budget_arms.log`，按 T(oracle α)/T(α=2) 计算，不考虑质量：
- arxiv：×3.81（np128）、×2.01（np512）；
- vogue：×1.37、×1.16；
- bge：×1.07；
- stella：≤×1.04；
- openai3-1536 和 openai3-3072：≤×1.01。

12 个配置中有 8 个，任何 per-query 方案最多只能快 7%。

**D. 与 α 有关的时间花在哪里**（α 4→100 增加的耗时）：精排占 80–90%，scan 的 top-ck 选择占 10–19%，top-k 占 0–1%。所以"先在 ck_max 下 scan，再预测 ck_q、只精排 ck_q"仍能拿到大部分可省的时间。

**E. 嵌套与 K_LOCAL：**
- 必要条件检查：某个 α 已找回的参考项，在更大的 α 下是否还在。4 个配置共 112000 对中有 13 对违反，全部在 vogue/512（0.046%），其余为 0。
- K_LOCAL=4 与 K_LOCAL=8 在 vogue/128 α=100 上，1000 条查询的 top-10 完全相同。
- 结论：前缀复用大概率成立，但不是严格保证；要直接验证需要 dump 全部查询的 top-ck 主码候选。

## 判断

- 在已经有 workload 级自适应 α 的前提下，per-query 精排在 openai3、bge、stella、openai3-1536 上没有值得做的空间。
- vogue 的理想上界是 ×1.14–1.37，实际可达的会更低：预测误差、拖尾、scan 仍按 ck_max 运行都会吃掉一部分。
- 唯一上界大的是 arxiv（×2–3.8），但 arxiv 没有 per-query dump，所以它的需求分布未知。另外它的饱和点超出 α=200，参考本身就不够大。

## arxiv 补测：在拿到数据之前固定的规则（2026-10-12）

**运行方式**：`run_arxiv_dump.sh`，不改内核，不开新版本目录。
- 使用与 arms6 相同的库（`jhq_v57_exp`）、相同参数和同一个 `JHQ_INDEX_CACHE` 目录，np ∈ {128, 512}，α ∈ {2, 4, 8, 16, 32, 64, 100, 200, 400}。
- α=400 是这个构建在 BLOCK=512 下能跑的上限附近：final top-k 内核没有申请超出默认值的共享内存，限制为 ck ≤ 5376；exact scan 的限制为 ck ≤ 7680。

**同一索引检查**：held-out（奇数查询）的 recall 必须在每个 α 上与 `budget_arms.log` 的 FIXED 结果逐位一致（日志精度 4 位小数）。
- 一致，说明这是论文测过的同一个索引，同时也说明查询结果不依赖同批的其他查询（arms6 是 500 条一批，这里是 1000 条一批）。
- 不一致，说明索引被重新训练（cache 不在了），或者结果依赖 batch 组成。这种情况下结论只代表"同配置的另一个索引"。

**两种 oracle**（对应 review 提出的两种）：
- 参考一致型：LF0 和 LF10，每条查询取能复现参考输出的最小 α。
- recall 约束型：GT10。在全部查询之间分配"最多丢 10 个真近邻"的预算，以最小化理想时间；逐查询损失截断在 0，小 α 偶然多找到的近邻不能抵扣预算。
- 两者都是离线上界。参考分别取 α=400 和 α=200 各报一次，因为 arxiv 在 200 时没有饱和。

**决策**：只看主场景（参考取最大 α、计时用 dump 自带的 QPS）下的 GT10 理想加速：
- ≥×1.5：GO，研究低开销的难度预测器，再测 GPU batch 的实际表现；
- ×1.2–1.5：MARGINAL；
- <×1.2：STOP，关闭 per-query 精排方向。

这些阈值来自 review 的建议，是约定而不是定理。LF10 和 sensitivity 场景一并报告，但不参与决策。

## 下一步（只有它能改变结论）

用现有二进制在 GPU 上为 arxiv 生成 per-query dump：方式与 `alpha_perquery.log` 为 vogue 和 openai3 做的相同，α 网格取 2..200，如果共享内存允许再加更大的 α。然后重跑本脚本。

- 如果 arxiv 在质量对齐下的 gap 明显（例如 ≥×1.5），再做预测器可行性研究。预测器需要全部查询的 top-ck 主码距离；v57 的 `JHQ_DUMP_TOPCK` 只写 query 0，所以这一步需要新版本目录（v60）。
- 如果 gap 很小，关闭这个方向。
