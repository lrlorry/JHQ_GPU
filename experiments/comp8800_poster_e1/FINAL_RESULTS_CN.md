# E1：JHQ-GPU v69 与 cuVS 基线的最终对照（COMP8800 海报主结果）

**结论先行。** 同一张 RTX 5090、同一组查询、同一 Recall@10、同一主机到主机计时口径（batch 1 000）下，在四个嵌入数据集上：

1. **对 CAGRA fp32（图索引）**：Recall@10 0.90–0.985 的整个区间里，JHQ-GPU v69 的吞吐都更高。768 维上高 1.10–1.51 倍，1 536/3 072 维上高 1.58–2.44 倍（插值）。所用显存约为 CAGRA fp32 的三分之一。例外只有 arXiv-768 的 0.99 一档，那里 CAGRA 快 1.4–2.1 倍。
2. **对 IVF-RaBitQ（最强的量化基线）**：Recall@10 不超过 0.97 时，JHQ 持平或更快：768 维 1.00–1.56 倍，1 536/3 072 维 1.13–1.93 倍（插值）。到 0.98 及以上，RaBitQ 大多更快：
   - Vogue 和 OpenAI3-3072 上快 2–12%；
   - OpenAI3-1536 上 0.985 时快 4%（0.98 一档受 JHQ 测点稀疏影响，插值和直接测量方向相反，不下结论）；
   - arXiv-768 上 0.985 时快 1.3 倍，0.99 时快 2.3 倍。

   RaBitQ 的最高 recall（0.994–0.996）也高于 JHQ（0.985–0.991）。
3. **CAGRA int8** 在 Recall@10 0.90–0.92 时是四个数据集上最快的方法（比 JHQ 快 1.2–2.1 倍），但它的上限只有 0.945–0.968。**在 Recall@10 = 0.97 处，JHQ-GPU 在四个数据集上都是吞吐最高的方法**；arXiv-768 上与 RaBitQ 打平。
4. 测量共 1 590 个点，0 个失败，0 个缺陷点（id 越界或行内重复）。另有 401 个点的返回结果在多次调用之间不完全一致，大多只是并列项顺序不同：RaBitQ 189 个、IVF-PQ 88 个、CAGRA 123 个、暴力搜索 1 个。这些点都保留，并在报告中说明。

这些结论只适用于 batch = 1 000、k = 10、这张卡和这四个数据集。

## 2. 实验设置

- **查询与评价**：每个数据集都用同一份 1 000 条查询和同一份 GT（宽度 ≥ 10）。Recall@10 = |返回的前 10 个 ∩ GT 的前 10 个| / 10。距离为平方 L2。
- **主口径 A（主机到主机）**：从主机内存里的 FP32 查询开始，到 top-10 的 id 和距离回到主机内存为止，包括：pinned 暂存、H2D、必要的查询预处理（CAGRA int8 的查询量化）、搜索、D2H、同步。每次调用回答全部 1 000 条查询。
- **辅助口径 B（设备常驻）**：查询已在 GPU 上，只计搜索加同步。JHQ 的 API 只接受主机指针，所以 JHQ 没有 B。
- **测量**：每个点先预热（JHQ 每轮 1 次，共 5 次；其他方法 3 次），再做 5 轮、每轮 24 次调用。每轮 QPS = 24 000 / 本轮总时间，取 5 轮的中位数。敏感性检验另用"1 000 / 中位单次调用延迟"计算 QPS。
- **索引**：每组构建参数只构建一次，所有搜索参数在同一个索引上扫。构建时间和显存单独记录，不计入搜索数字。
- **内存池**：RaBitQ 的 RAFT workspace 使用 2 GiB 池，cuVS 的 Python 方法使用 RMM 池（cuVS 自己的基准程序也是这样做的）。两者都是在构建完成、显存测量完毕之后才开启。

| 方法 | 参数网格 |
|---|---|
| JHQ-GPU v69 | M = d/8，B = 8，Br = 8（主码每维 1 bit，残差每维 8 bit）；nlist 4096（vogue）或 8192（其余三个）；nprobe 16–1024；α 在论文值的 ¼ 到 64 倍之间按需扩展（只有在覆盖不到目标 recall 时才扩展）；调度 G = −1 |
| CAGRA fp32 / int8 | graph_degree 32、64（intermediate 128，用 ivf_pq 建图）；itopk 32–512；search_width 1、2、4、8；int8 用 cuVS 标量量化（quantile 0.99），查询在计时区内量化 |
| IVF-RaBitQ | bits_per_dim 9（与 JHQ Br=8 预算相当）、8、4；nlist 与 JHQ 相同（两个 OpenAI3 数据集另加 4096）；四种搜索模式；n_probes 16–1024 |
| IVF-PQ | nlist 与 JHQ 相同；pq_dim 在 768、1536 维为 d/4、d/2、d，在 3072 维为 d/8、d/4、d/2（pq_bits 8）；LUT 和内部距离用 fp32 或 fp16；n_probes 16–512 |
| GPU 暴力搜索 | cuVS brute_force，FP32，作为"精确搜索"参考 |

## 6. 测量波动与结果稳定性

5 轮之间的离散度 =（最大 − 最小）/ 中位数：

| 方法 | 中位离散度 | 90 分位 | 离散度 > 5% 的点 |
|---|---|---|---|
| JHQ | 1.1–1.4% | 2.8–4.6% | 1–3 个 / 数据集 |
| CAGRA fp32 | 0.2–0.7% | | |
| CAGRA int8 | 0.6–1.5% | | |
| IVF-PQ | 0.2–0.4% | | |
| IVF-RaBitQ | 2.9–5.3% | 20–33% | 36–52%（单点最大 90%） |

RaBitQ 离散度偏大，来自它搜索内部偶发的 30–60 ms 单次调用（分段诊断见 FAIRNESS_AUDIT.md 第 6 节第 4 项）。5 轮取中位数能抵消大部分尖峰，敏感性检验也表明结论不受影响。

结果确定性：
- **CAGRA**：大多数配置完全确定，部分宽搜索配置有少量差异。
- **RaBitQ**：两次调用之间，1 000 行里约 8–12 行的 id 集合不同、40–50 行只是顺序不同，recall 在第 4 位小数波动。
- **暴力搜索和 IVF-PQ**：只有并列项的顺序差异。
- **JHQ**：每个点都做了 G = −1 与 G = 0 的逐查询比对，全部通过（BP_OK）。

所有这些点都保留在前沿里，逐点说明见 `E1_TABLES.md` 末尾。

## 7. 公平性修正对结果的影响

这次的口径比 9 月的旧数据对基线更有利：
- RaBitQ 用 pinned 上传、内存池和更密的 n_probes 网格。例如 vogue np=128 时，9 月日志（bits=8）是 0.9566 / 180K；这次 bits=9 LUT16 是 0.9576 / 263K。
- cuVS 的 Python 方法复用句柄、预分配输出。
- CAGRA int8 的查询量化计入了时间，这一项对 int8 不利，属于纠正；它的 A 与 B 两种口径相差约 0.3 ms。

完整审计见 `FAIRNESS_AUDIT.md`。

和历史结论的关系（只作锚点，不与本次数据混用）：
- ADC 草稿时期的版本在 768 维上比 CAGRA fp32 慢 1.45–2.03 倍。这次 v69 在同类数据上反过来快 1.1–1.5 倍。差别来自 v61 之后的精排与 pipeline 优化。
- 9 月 9 日的提交记录里，JHQ 对 RaBitQ 在 768 维上基本持平、高 recall 落后，与这次的结论方向一致。

## 8. 异常、限制与未完成

- **范围**：只有一张卡、一个 batch（1 000）、k = 10。不推广到小 batch、其他 GPU 或其他 k。
- **小 batch 外部对照没有做**：简报里这是可选项。海报上的小 batch 结论只能用内部数据（v61 → v65 → v69）。
- **JHQ 没有 B 口径**；JHQ 的显存是近似值（进程总量减 context）。
- **Python 调用开销**：CAGRA 和 IVF-PQ 经 cuVS 的 Python 封装，每次调用多出几十 µs 的开销，相对 1–100 ms 的单次调用可以忽略，而且这一项偏向 JHQ。RaBitQ 是 C++。
- **CAGRA 构建参数**用 cuVS 默认值（intermediate 128，ivf_pq 建图），没有试 nn_descent 或更大的 degree。
- **IVF-PQ + refine 没有正式运行**：冒烟测试中它异常慢（R = 0.90 时 14.5K QPS），原因未查明。
- **JHQ 的前沿比基线稀**：每个数据集 27–39 个点，基线 54–264 个。所以表中同时给出插值比和直接测量比；两者不一致的格子（如 OpenAI3-1536 在 0.96 和 0.98 处对 RaBitQ）属于网格造成的不确定，海报上不引用这些格子的单点数字。
- **一个已知断崖如实保留**：arXiv np=64 时 α=50（ck=500）比 α=100 慢，这是扫描缓冲的 headroom 断崖，见 practical_opt 报告。
- 无 OOM、无超时、无失败记录（`E1_failures.csv` 为空）。

## 9. 对 JHQ-GPU 的客观结论

- 在 Recall@10 约 0.94–0.98 这一段，JHQ-GPU v69 是这张卡上很有竞争力的方法：
  - 对图索引 CAGRA fp32，吞吐高 1.1–2.4 倍，显存只用约三分之一；
  - 对 IVF-RaBitQ，在 0.97 及以下持平或更快；
  - 在 0.97 这一档，四个数据集上都是最快或并列最快。
- 它不是处处最快：
  - 低 recall（0.90–0.92）时 CAGRA int8 更快；
  - 0.98 以上 IVF-RaBitQ 更快（arXiv 上差距明显）；
  - 0.99 以上 JHQ 基本覆盖不到。CAGRA fp32 和 RaBitQ 能到 0.992–0.9995，JHQ 只到 0.985–0.991。
- 1 536 和 3 072 维上，JHQ 对 CAGRA fp32 和 RaBitQ 的领先都比 768 维大。这是经验观察：本次设置 M = d/8，JHQ 的主码也随维度增长，所以这个趋势的机制没有被 E1 证明。
