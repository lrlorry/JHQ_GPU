# v61 Warp-Cooperative Refinement：正确性与六数据集对比

2026-10-12/13 · RTX 5090（AutoDL）· commit `b37efa4` · 原始数据：`raw/` · 完整表格：`raw/summary.md`

## 结论

1. **正确性通过。**
   - 32-bit 读取版本（L1）在 13 个配置、全部查询上，返回的 id 和距离都与原内核**逐位一致**。
   - 多 lane 版本（L8/16/32）的距离相对误差 ≤1.6e-6，来自浮点求和顺序不同。每个配置至少 996/1000 条查询的 id 顺序完全一致、998/1000 条的 id 集合一致。凡是集合不同的查询，第 k 个距离只差 ≤4.9e-7，属于近似并列。
   - Recall@10 只有一处变化：vogue/512 的 L8 和 L32 为 +0.0002。
   - compute-sanitizer 的 memcheck、racecheck、synccheck 全部 0 错误。
2. **没有任何配置变慢。** 在论文 sampled-rule α 下，12 个配置用 L16 的端到端加速为 **×1.015–1.789**；arxiv/128 在 full-pool 预算 α=200 下为 ×2.383。refine 内核本身快了 **×1.97–8.81**。
3. **收益大小由 refine 在搜索中的时间占比决定**，符合 Amdahl 定律：
   - 占比大的配置收益大：arxiv/128 占 59%，端到端 ×1.79；vogue/128 占 33%，×1.24。
   - scan 占主导的配置收益接近 0：stella/512 只占 2%，×1.015；bge/512 占 11%，×1.04。
4. **两项改动的收益分开看：**
   - 32-bit 读取（L0→L1）使内核快 ×1.23–2.05；
   - 多 lane 映射（L1→L16）再快 ×1.54–5.64。
5. **L16 适合作为唯一默认值。** 13 个配置中，它的端到端都在最优 L 的 1.1% 以内，内核在 11 个配置里最快。另外 2 个是 bge-m3，L8 的内核快约 5%，端到端只差 ≤1%。

## 1. 实现（`jhq_v61_warp_refine`）

v61 = v58 加上可在运行时切换的 refine 内核，没有其他改动；v58、v60 和论文都未修改。

| lanes | 内核 | 与 v58 的关系 |
|---|---|---|
| 0（默认） | `residual_refine_fused_kernel`：每线程一个候选，逐字节读码字 | 就是 v58，没有改动 |
| 1 | `residual_refine_group_kernel<BR,1>`：每线程一个候选，按 32-bit 字读码字 | 求和顺序与 0 相同，结果逐位一致 |
| 8/16/32 | `residual_refine_group_kernel<BR,L>`：L 个 lane 处理一个候选，按 lane 跨步分摊码字，最后用 butterfly 归约 | 计算同一个分数，只是求和顺序不同 |

- 切换方式：调用 `jhq_gpu::set_refine_lanes()`，或在启动时设置环境变量 `JHQ_REFINE_LANES`。
- 当前选用的内核也是 CUDA graph 缓存键的一部分，切换内核会触发重新 capture，旧 graph 不会被重放。
- 约束检查：Ds 必须是每个字所含维数的倍数（Br=8 时为 4），bpv 必须是 4 的倍数，launch 时会检查。论文的 6 个数据集都是 Ds=8、Br=8。

## 2. 实验设置

**索引**：沿用 `run_budget_arms6.sh` 的参数，并使用 arms6 的 trained-state cache，也就是论文 Table budget_current 测量的同一份索引。12 个进程的训练耗时都只有 14–161 ms，说明全部命中了 cache；不命中时训练需要好几分钟。

**配置**：6 个数据集 × np ∈ {128, 512}，α 取 Table budget_current 中 S=128 时 sampled-rule 的中位数：

| 数据集 | np128 α | np512 α |
|---|---:|---:|
| vogue-768 | 64 | 64 |
| arxiv-768 | 100（另测 200，标为 full-pool/oracle 高预算） | 200 |
| openai3-1536 | 8 | 8 |
| openai3-3072 | 4 | 4 |
| bge-m3 | 32 | 64 |
| stella | 16 | 16 |

**测量 harness**（`examples/demo_jhq_v61_refine_ab.cu`）：
- 每个（数据集, np）只起一个进程、只建一次索引，所有内核都在这同一份索引、同一组查询、同一个计时范围下测量。
- 计时范围和论文 QPS 所用的 demo 一致：`search()` 外围的墙钟时间，包括 H2D 拷贝、graph launch、D2H 拷贝和同步。
- 共 5 轮。每轮里各内核的执行顺序轮换；每个内核先做一次不计时的搜索（重新 capture graph），再计时 3 次取平均。
- 加速比在同一轮内配对计算，报告中位数和 [最小, 最大]。
- 每次搜索 1000 条查询（stella 的查询文件是 999 条），恰好一个 batch，k=10。

**内核耗时**：用 nsys（`--cuda-graph-trace=node`）记录，每个配置 5 次搜索，取 refine 内核每次 launch 耗时的中位数。不同 lanes 是不同的模板实例，所以可以按内核名分开统计。

**内存安全**：compute-sanitizer 只检查 refine 和 top-k 内核，每次 64 条查询，每次运行都覆盖全部 5 个内核：
- memcheck：6 个数据集，np=128；
- racecheck 和 synccheck：vogue（码本在共享内存）和 openai3-3072（码本在全局内存，BLOCK=1024）。

**环境**（完整记录见 `raw/env.txt`）：
- RTX 5090，驱动 595.71.05，CUDA 13.0（V13.0.88），nsys 2025.3.1，g++ 11.4；
- CMake Release，`CMAKE_CUDA_ARCHITECTURES=80`：编译出 compute_80 的 PTX，在 5090 上由驱动 JIT 编译。这和服务器以往的构建配置相同，所有内核都在同一条件下比较。
- 编译选项：`-O3 --use_fast_math`，以及与 v58 相同的 `JHQ_PAPER_FAITHFUL` 等宏定义。

## 3. 正确性

| 检查项 | 结果 |
|---|---|
| L1 与 L0 的 id 和距离逐位比较 | 13 个配置全部查询逐位一致（1000/1000，stella 999/999） |
| L8/16/32 与 L0 的 id 顺序一致 | 每个配置 ≥996/1000 |
| L8/16/32 与 L0 的 id 集合一致 | 每个配置 ≥998/1000 |
| 同一 id 的距离相对误差 | ≤1.6e-6 |
| id 集合不同时，第 k 个距离的相对差 | ≤4.9e-7（只出现在 vogue/512），属于近似并列 |
| Recall@10 | 除 vogue/512 L8、L32 为 +0.0002 外全部相同 |
| memcheck | 6 个数据集均为 0 errors |
| racecheck | 0 hazards（0 errors，0 warnings）× 2 |
| synccheck | 0 errors × 2 |

逐查询的 id 和距离保存在 `raw/ab/<数据集>_np<np>_a<α>_L<lanes>.{ivecs,fvecs}`，需要时可以再拿来比对。

## 5. 两项收益分别来自哪里

这一节的机制解释是根据内核耗时在不同配置之间的变化规律推断出来的。这个容器读不到硬件计数器（Nsight Compute 报 `ERR_NVGPUCTRPERM`），所以没有用 profiler 指标直接验证。

**32-bit 读取（L0→L1，内核 ×1.23–2.05）。** 映射方式不变，每条载入指令读 4 个字节而不是 1 个，载入和地址计算都减少到 1/4。
- 收益最大的是 vogue 和 arxiv（×1.89–2.06）。它们 M=96，残差码本放得进共享内存，每维的开销主要是取码字的那次载入。
- 收益较小的是 M≥128 的数据集：bge、stella、openai3 为 ×1.23–1.56。它们的码本放在全局内存里，每维都要做一次全局内存的码本查找，这部分开销读取方式改变不了。

**多 lane 映射（L1→L16，内核 ×1.54–5.64）。** 原来每个候选由一个线程串行走完 d 维；现在由 L 个 lane 分摊，相邻 lane 读同一码字里相邻的字。
- 收益最大的是 openai3-3072（×5.6）：α=4 时 ck=40、BLOCK=1024、d=3072，原内核一个 block 里只有 40 个线程在工作，每个线程要串行走 3072 维。
- arxiv（×2.9–3.5）和 vogue（×2.0）的 ck 较大（640–2000），收益主要来自缩短每个候选的串行路径和改善合并访存。
- bge 的收益最小（×1.5–1.6），因为它的瓶颈在全局内存里的码本查找。

## 6. L 怎么选

L16 的端到端在每个配置上都达到最优 L 的 98.9% 以上，内核在 13 个配置中有 11 个最快。剩下的 bge-m3（两个 np）是 L8 最快，比 L16 快 4.8–5.6%，但端到端只差 ≤1%。

L32 在 bge 和 stella 上明显较差，内核比 L8 慢 1.5–1.8 倍。这两个数据集 M=128、码本在全局内存。推测原因是：一个候选用 32 个 lane 时，同一 warp 里只有一个候选在推进，无法掩盖查表延迟。这一点没有用计数器验证。

L8、L16、L32 之间的端到端差异大多落在 5 轮测量的波动范围内，所以选 L 时以 nsys 的内核中位数为准。**建议默认 L16，不按数据集分别调。**

## 7. 退化与异常（全部列出）

- **没有任何配置的中位数比 L0 慢。** 最接近的是 stella/512 的 L1：中位数 ×1.004，5 轮中最慢一轮 ×0.999，属于噪声。
- **vogue/512 的 L8 和 L32 recall +0.0002**，即一万个槽位里多对了 2 个；L16 没变。原因是浮点求和顺序不同，让近似并列的第 k 名换了人（第 k 个距离只差 4.9e-7）。这不是退化，但它说明 L>1 的结果并不与原内核逐位一致。
- **部分轮次偏离较大。** 52 个（配置 × 内核）组合中，40 个的轮间波动在 ±3% 以内。偏离较大的集中在 np128 的 4 个配置，都是某一轮明显偏低：
  - openai3-3072 L16：−13.8% / +7.0%，即 [×1.009, ×1.252]；
  - arxiv α=100 L16：−9.5%；
  - arxiv α=200 L8：−7.6%；
  - vogue L8：−7.2%。

  这些都是单轮偏低，中位数不受影响。openai3-3072 的中位数 ×1.171 也和 v60 当时测的 ×1.18 一致。GPU 时钟没有锁定，见局限。
- **在 scan 主导的配置上收益很小**：np=512 下 stella、bge、openai3 的端到端只有 ×1.015–1.06。这是 Amdahl 定律的结果，不是内核的问题：这些配置里 refine 只占 2–11% 的时间。
- **服务器端自动生成的汇总**把 racecheck 误判为"没跑完"，因为它的汇总行是 `RACECHECK SUMMARY`。我已在本地修正汇总脚本，并用同一份原始文件重新生成了 `raw/summary.md`；原始日志本身没有任何改动。

## 8. 局限

- 只测了一种硬件和设置：RTX 5090、1000 条查询一个 batch、k=10、np ∈ {128, 512}、论文的 sampled-rule α，外加 arxiv/128 的 α=200。**没有测完整的 Recall–QPS frontier。**
- 不要把本报告的绝对 QPS 和论文 Table budget_current 直接比较。那张表测的是 500 条 held-out 查询为一个 batch，这里是全部 1000 条一个 batch。本报告只主张同一 harness 内部的比值。
- 构建用的是 compute_80 的 PTX，由驱动 JIT 编译到 5090。换成原生 sm_120 编译后，绝对性能和各 L 之间的相对差距都可能变化。
- refine 的线程块大小直接沿用 `JHQ_BLOCK`（512，openai3-3072 为 1024），没有针对每个 L 单独调优。
- Br=4 的代码路径没有被测到，因为论文配置全是 Br=8。
- sanitizer 只检查了 refine 和 top-k 内核，每次 64 条查询；racecheck 和 synccheck 只覆盖两个数据集。
- 计时有 5 轮 × 3 次，但 GPU 时钟没有锁定，见上面 openai3-3072 的波动。

## 9. 下一步（由你决定）

正确性和六数据集对比都已完成，结果是 L16 在所有配置上都不变慢。如果要继续，我建议：
1. 新开 v62，把 L16 设为默认；v61 保留作为对照。
2. 完整的 Recall–QPS frontier 只比较 L0 和 L16 两个内核，扫 α × np，重点看 arxiv（refine 占主导）和 vogue。不必再扫全部 L。
